# v1.3 完整代码、可用性与安全审计

审计日期：2026-10-29（Asia/Shanghai）。基线：`v1.3`，提交 `299395bee80394ae35e0743777fecf85c5e0cf1d`。本地 HEAD 与 GitHub main、最新 Release 一致；开始审计时工作区干净。

## 1. 结论

**应用的主要功能真实可用，但当前版本仍有需要修复的边界缺陷，不能据现有测试认定为全面无问题。** 本轮使用正式发行 EXE 实际完成公网采集、历史读取、三格式导出；通过原生窗口点击保存并读回文件。两套真实规则源下载成功，合并、分页和完整复制下载也跑通。界面统计来自任务和请求数据，未发现以固定假数据代替正常业务的实现。

本报告列出 **17 项问题：P1 1 项、P2 9 项、P3 7 项**，另列 **1 项条件性安全加固风险**。其中既有真实界面/API 复现，也有隔离夹具复现和静态确认；证据类型逐项注明。不是将 17 项全部称作安全漏洞，也不把扫描器的 37 条二进制告警当作 37 个已证实可利用漏洞。

最优先处理的是发行 EXE 使用的旧 Go 标准库，其次是活动任务控制、跳转后的探索逻辑、草稿与预览失效管理、中文文件名和启动错误传递。没有发现需要推倒重写整个项目的依据；存在少量遗留代码、重复版本信息和过密 JSX，适合局部整理。

可开发的新功能单列在[扩展清单](v1.3-可开发与丰富功能-2026-10-29.md)，不纳入上述问题数量。

## 4. 逐项发现、影响与建议

### A01 — P1：发行 EXE 使用旧 Go 安全基线

**证据：** `go version -m` 读取正式 EXE 为 Go 1.26.2。`govulncheck` 源码符号扫描报告 21 项标准库问题；二进制扫描报告 37 项，包括模块级匹配。报告分别保存在 `govulncheck.log`、`govulncheck-binary.log`，逐项摘要见附录。

**已核对的实际关联：** [GO-2026-6609](https://pkg.go.dev/vuln/GO-2026-6609) 影响文件服务中的多 Range 解析，项目通过 `backend/internal/webui/webui.go:15` 使用 `http.FileServer`；[GO-2026-6218](https://pkg.go.dev/vuln/GO-2026-6218) 涉及 URL 相对路径解析，探索器在 `backend/internal/crawler/crawler.go:21` 调用 `ResolveReference`。这些有代码关联，但本轮没有执行耗尽服务的攻击验证。默认回环、Host/Origin 防护会限制外部攻击路径，不会消除旧标准库本身的问题。

[GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809) 的证书信任修复覆盖更窄的平台/信任库场景，不能把它描述成当前 Windows 上任何证书都可绕过。二进制中的 `x/net/html` 等模块告警也不能直接认定为本项目可触发 XSS；源码扫描未显示对应渲染符号调用。

**建议：** 使用至少包含上述修复的 Go 1.26.10，或相应受维护的已修复分支重新构建；核对 `x/net` 已修复版本并重新扫描。保留符号可达性与运行条件分析，增加 CI 安全扫描，重新完成实际浏览器、导出和桌面生命周期验证。升级、重打包和发布本轮均未执行。

### A02 — P2：查看历史会丢失停止入口

**复现：** 启动一个真实扫描，在任务仍为 `starting` 时打开历史，再打开已完成任务。后台扫描仍活动，但页面“停止采集”数量变为 0，“开始分析”反而可点击。证据为 `ui-probes.json` 的 `historyHidesActiveStop` 和 `chrome-active-history-1440x900.png`。

**原因：** `frontend/src/pages/App.tsx:49` 仅通过当前展示的 `task` 判断是否运行；`:118` 打开历史时直接替换当前任务 ID。扫描管理器的全局活动任务与当前查看任务没有分开管理。

**影响：** 用户需要重新去历史寻找运行中的任务才能停止；尝试新扫描会遭后端 busy 拒绝。限制并发的后端逻辑仍正常，未发生双任务同时执行。

**建议：** 保留独立的活动任务 ID/状态，在历史阅读期间维持固定“返回正在采集 / 停止采集”入口，开始按钮也依据全局活动状态判断；补“活动任务 + 历史浏览”的回归。

### A03 — P2：规范域名跳转使探索退化为单页

**复现：** 输入 `scan.test`，测试站跳转到 `www.scan.test`，最终页面包含 `/second`。真实 Chrome 加载成功，但 `/second` 被记为“第三方页面，未主动导航”，仅访问 1 页，任务显示 `completed`。测试用了精确临时映射，不曾放宽生产私网策略。见 `scanner-boundary-probes.log`。

**原因：** `backend/internal/scanner/engine.go:140` 在最初输入上固定 origin；`:253–261` 从跳转后的页面提取链接时仍使用旧 origin。HTTP→HTTPS、裸域→www、规范端口等变化都有同类条件。

**影响：** 用户选择自动探索，却可能误以为最终网站的正常内部链接已处理。该现象不等于全部跳转场景都会失败。

**建议：** 在完成地址校验后识别最终主文档来源；明确提示并让用户确认是否以最终来源继续，或提示改用最终 URL 重扫。不能直接把任意跨站跳转全部扩入探索范围。结束原因应说明因来源变化缩小了覆盖。

### A04 — P2：中文文件名长度标准不一致

**复现：** 60 个“测”加 `.yaml`，共 65 字符、185 UTF-8 字节。导出器允许生成该文件名；正式桌面 API 返回 HTTP 400“导出文件名不合法”。ASCII 对照正常 HTTP 200。见 `native-filenames.json`、`boundary-probes.log`。

**原因：** `backend/internal/exporter/exporter.go:37` 按 100 个 rune 截断；`backend/internal/portable/paths.go:66` 按 180 字节拒绝。预览侧没有同样的约束。

**建议：** 统一跨端文件名规则，在输入/预览时就显示可理解的长度提示；自动截断时保留完整字符、扩展名、同名编号和 `.sources.txt` 余量。测试应覆盖中文、混合字符与来源说明名称。

### A05 — P2：规则更新会静默丢弃临时草稿

**复现：** 打开真实 Facebook 原文，追加 30 字符的审计注释。只在测试响应里改变另一来源 v2fly 的版本，未改变所选 blackmatrix7 来源。一次轮询后编辑区从 19454 字符回到 19424 字符，注释消失。见 `editor-and-colors.json`。版本变化是显式夹具，未宣称上游恰好在编辑期间真的更新。

**原因：** `frontend/src/components/RuleLibrary.tsx:24` 汇总所有来源版本，`:37–56` 的读取 effect 依赖整个汇总；任一来源改变都会重新执行 `setDraft`。

**建议：** 仅监听当前所选分类所属的来源/内容版本，并跟踪 dirty 状态。更新到达时保留草稿，用简短提示提供查看新原文、复制草稿或恢复；避免再增加多级编辑页面。

### A06 — P2：缓存更新不会使合并预览失效

**复现：** 对真实已生成预览，测试让分类轮询返回新的版本元数据。轮询确有发生，后续 `/api/export` 调用数仍为 0，下载保持可用。见 `ui-probes.json` 的 `stalePreviewAfterSourceMetadataChange`。此探针验证失效机制，未伪造真实的上游更新事件。

**原因：** `frontend/src/components/ExportDialog.tsx:72–84` 的 job/key 不包括被选分类的版本或内容摘要；`:61` 在 ID 未改变时保留同一个选择数组；`:115` 因参数 key 相同继续认为预览新鲜。

**影响：** 分类缓存和已显示的预览可能来自不同快照；用户以为正在导出当前缓存，实得旧规则。归属信息仍是旧预览的版本，没有证据表明来源被伪造。

**建议：** 将所选分类版本/内容摘要纳入预览快照，变化时暂停下载并重新计算或提示确认；保留用户排除项，分类消失时明确说明，不静默扩大选择。

### A07 — P2：启动错误先删除后读取

**静态确认：** `backend/internal/desktop/desktop_windows.go:164` 删除 `window-error.txt`，`:175` 才调用 `reportedError()` 读取它。`desktop/errors.go` 的保存/读取辅助函数即便单测通过，也无法覆盖此监督进程顺序。

**影响：** 缺少 WebView2、初始化失败等 worker 错误会退化为笼统异常退出提示，原本准备提供给用户的明确原因丢失。当前机器已有 Runtime；本轮没有卸载组件来伪造缺失环境。

**建议：** 先读取并保留错误内容，再清理文件；将“worker 写错误 → supervisor 展示”的完整路径加入测试，在专用干净环境验证缺少 Runtime 的提示。

### A08 — P2：清理缓存改变了持久化偏好

**复现：** 开启 v2fly 自动更新后执行 `Clear()`，`AutoUpdate` 从 true 变为 false。见 `boundary-probes.log`；探针未启动后台更新线程，避免下载时序干扰。

**原因：** `backend/internal/storage/storage.go:265` 删除整个 `rule_sources`；`backend/internal/rules/manager.go:564–568` 恢复默认来源，连自动更新开关一起重置。界面按钮仅称“清理规则缓存”，未说明偏好会改变。

**建议：** 将更新偏好与可删除快照分开存储，或清理时明确保留开关。若保留开关会立即重新下载，应在操作旁简短说明，让用户可预期。

### A09 — P2：解析资源边界存在漏检

**复现：** 在小于单文件 2 MiB 限制的文件内放 100001 条直接规则，当前 `DLCParser.Parse` 成功返回 100001 条，超过声明的 `MaxCategoryRules=100000`。见 `boundary-probes.log`。

**原因：** `backend/internal/rules/parser.go:273` 先复制直接条目；`:296` 的数量检查仅在 include 循环内，纯直接规则没有经过检查。同时 `Parse/resolve` 不接收 context；`manager.go:476–480` 只在每个分类开始前检查取消。重复 include 可反复解析相同子图，深度限制不能替代工作量预算。

**影响边界：** 普通用户不能通过 API 上传自定义规则源；主要风险来自上游异常内容/供应链变化。当前真实 2221 类均成功加载，没有拿构造文件冒充上游现状。没有执行极端耗尽测试。

**建议：** 直接条目、include、属性过滤和最终唯一规则统一校验上限；引入总访问节点/条目预算及 context 检查，必要时缓存子图解析结果并保留属性变体语义。任何取消/失败仍保持旧快照。

### A10 — P3：请求上限处的重定向记录被串改

**隔离复现：** 在请求数已到 20000 的边界，旧跳收到 302 并结束，新跳因上限未加入；随后新跳 200 响应却把旧 URL 记录改成 200、`responding`。见 `scanner-boundary-probes.log`，这是构造 CDP 事件，不是实际发起了两万条请求。

**原因：** `backend/internal/scanner/recorder.go:116–118` 拒绝新记录时，`:146` 使用的 `active[RequestID]` 仍指向前一跳；后续 `response()` 更新了它。

**建议：** 拒绝新跳时解除该 RequestID 的旧映射，忽略后续未记录跳的事件；保留旧跳 302/redirected。补恰好上限及上限前后的重定向测试。

### A11 — P3：命中结果被静默截断

**隔离复现：** 70 个分类均命中同一观察主机，返回结果只有 60 个，提示没有“截断”信息。见 `matcher-boundary-probes.log`。

**原因：** `backend/internal/matcher/matcher.go:171–172` 直接切片；API/UI 没有匹配总数或截断标志。不是认定所有日常站点都会超过 60 类。

**建议：** 至少返回真实总数和 `truncated`，显示“前 60 项”；需要时再增加分页/检索。不要让展示数量被误认为全部实际命中数量。

### A12 — P3：桌面导出没有使用统一严格 JSON 解码

**真实复现：** 向隔离桌面实例提交合法保存对象后追加 `{}`，接口仍返回 HTTP 200 并保存文件。普通 `/api/export` 已有单对象校验并拒绝此形式。见 `native-api-probes.json`。

**原因：** `backend/internal/api/api.go:228–230` 只 Decode 一次，没有未知字段检查或 EOF 校验，与 `decodeLimit()` 的行为不同。

**影响边界：** 本轮未发现由此导致路径穿越或命令执行；Host/Origin/CSRF 与保存目录限制仍有效。这是接口合同不一致，不能夸大成任意写文件漏洞。

**建议：** 复用统一解码器，保留桌面内容大小限制；增加多对象、未知字段、超限、空值的接口回归。

### A13 — P3：部分小文字颜色过浅

**证据：** `frontend/src/style.css:40` 将 12px 行号固定为 `#888`，浅色预览背景经叠加约为 `#f5f5f5`，稳态对比度约 **3.246:1**。`:47` 将未勾选规则 code 的透明度设为 .55，按当前浅色文字/行背景计算约 **3.648:1**。这些条目仍可阅读并重新选择；不是禁用按钮。

计算见 `contrast-calculation.json`，依据当前 CSS 与浏览器样式，按动画结束后的 opacity=1 计算，没有把入场动画中间帧当成稳定颜色。以普通小文字 4.5:1 为检查标准，参见 [W3C SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。这不是完整 WCAG 合规认证。

**建议：** 行号改为随主题的足够深/亮的文字色；未选择状态用背景、复选框和轻微视觉差异表示，保留规则文字可读性。当前主要正文、主按钮和两种主题未发现同等明显的整体颜色冲突，不额外罗列没有证据的问题。

### A14 — P3：产品不同位置的版本号不一致

**证据：** `frontend/src/components/SettingsDialog.tsx:65` 的页脚仍为 v1.2；`scripts/collect-licenses.ps1:6` 的生成标题仍为 v1.1；当前主界面、EXE 资源、包和模型版本为 1.3。`docs/ARCHITECTURE.md:1` 的标题也仍标 v1.2，正文已有 v1.3 内容。

**影响：** 用户容易误以为运行了旧版，AI/维护者需要跨多个文件猜测真实版本。历史验收报告里的旧版本号是历史事实，不应批量替换。

**建议：** 产品版本由单一构建元数据生成，页脚/资源/许可证标题引用它；架构文档采用不绑定版本的标题，历史报告保持原样。

### A15 — P3：存在小规模遗留与阅读维护负担

**引用检查：** `config.DataDir()` 仅定义未被调用；`rules.Manager.LoadForTarget()` 未进入生产流程；`testsite.Port()` 没有调用；`rules.Matches()` 仅被自己的规则测试使用，生产匹配走独立索引实现；`config.example.json` 没有配置文件加载入口或使用说明。不能据此把全部数据模型字段或测试工具认定为无用代码。

TS 的 `noUnusedLocals/noUnusedParameters` 与生产构建通过，前端模块均有引用，没有发现大批废弃组件仍参与主流程。另一方面，多处长行 JSX 把整段表格、弹窗或多个事件处理挤在一行，规则管理器和导出弹窗也集中承担多个职责，增加审阅、补丁定位和 AI 上下文成本。

**建议：** 小步移除/解释未接入函数与配置样例；对规则匹配测试保留真实生产路径覆盖；引入统一格式化，按明确职责拆分少量子组件/状态逻辑。不要仅因文件长就拆出更多层级，也不要为了这次审计做全仓重写。

### A16 — P2：Linux 下载说明缺少对应成品

**实时证据：** [v1.3 Release](https://github.com/Kokomi-maomeng/Castorice-WebRuleAnalyzer/releases/tag/v1.3) 的附件仅有 Windows ZIP 和 `SHA256SUMS-v1.3.txt`，没有 Linux 二进制包。README 的 Linux 章节却直接从“解压 Linux amd64 包”开始，普通用户从最新下载页无法完成这一步。GitHub 自动生成的 Source code 不等于已编译 Linux 包。

**建议：** 先把 README 写清“当前 Release 提供 Windows 成品；Linux 需自行构建”的实际状态，并给出可执行的构建/运行路径。若决定交付 Linux 成品，另行构建、实机验证、打包校验并发布；本轮没有擅自补发附件。

### A17 — P3：导出与编辑的最后一步说明不够直接

**发现：** 默认 Clash 策略组固定为 `dibao`，应用不会在用户代理客户端中创建此组。文档介绍了选择和下载，却缺少最小的“三格式分别放到哪里、策略名如何对应现有组”的操作例子。Provider 与 sing-box 产物也只是可接入的规则文件，不是完整客户端配置。本轮验证了结构和文件，未验证客户端实际转发。

规则编辑器界面写“可选中、编辑、复制”，但“只改变临时文本，不改变匹配缓存”的明确解释主要在用户说明文件，界面不直接提示；用户可能编辑后直接重新匹配，期待不相符的结果。

**建议：** 策略组字段增加一句“需与客户端已有策略组一致”；下载旁提供一个简短帮助入口，文档各给一个最小接入示例。编辑器底部明确“临时编辑，仅用于复制/下载，不改变匹配缓存”。优先替换现有文字，不增加更多卡片和多级页面。这是现有流程的说明补齐，不把一键配置客户端等新功能算作缺陷。

## 5. 安全检查中有效的保护与剩余风险

### 5.1 已验证或审读确认的保护

- 输入只允许 HTTP(S)，拒绝凭据和非法端口；普通 API 不能启用私网测试白名单。
- 私网、回环、元数据、公私混合 DNS 答案受到拦截；保护代理每次连接校验并拨号到字面 IP，避免校验后再次解析改变目标。真实浏览器私网重定向回归通过。
- 已知 Fake-IP 使用独立 HTTPS DNS 后仍执行地址校验；不会借此放行真实私网。固定端点 DNS 实测通过。
- Host、Origin、cross-site 与随机写令牌校验通过负向测试。静态页面已有 CSP，包含 `frame-ancestors 'none'`；不能因为 API guard 本身未设置该字段而误报整个页面可被 iframe 点击劫持。
- 未发现生产代码启用 `--no-sandbox`、忽略 TLS 证书或把请求 Cookie/正文保存进数据模型的实现。测试 TLS 的 `InsecureSkipVerify` 位于测试代码，不计为生产漏洞。
- SQLite 查询使用参数绑定；桌面保存限制在 exports、限制扩展名并独占创建；路径穿越回归有效。React 以文本呈现来源/请求/原文，没有发现将这些内容送入 HTML 注入接口的主流程。
- URL 查询值脱敏、已知敏感路径处理和独立临时浏览器 Profile 有实现与回归；这不等于所有业务路径、主机名和历史内容都不敏感。

本轮没有确认可直接利用的应用级 RCE、SQL 注入、任意路径写入或现成凭据泄露链；这是一轮有界审计结果，不是“保证没有漏洞”。

### 5.2 R01：Docker 外层隔离被放宽（条件性加固风险）

`compose.yaml:11–13` 使用 `seccomp:unconfined`，AppArmor 默认也是 unconfined；附带 AppArmor profile 本身采用 `flags=(unconfined)`。非 root 和 Chromium 自身沙箱仍存在，也没有配置 privileged，但外层对系统调用和文件访问的限制显著少于默认保护。

这是为 Chromium 用户命名空间兼容作出的当前取舍，不是本轮证明了容器逃逸。应用会访问不可信网站，应在专用测试环境验证只开放必要调用的 seccomp/AppArmor 规则，并记录宿主发行版差异。本轮没有启动本机 Docker，也没有改宿主安全设置。

### 5.3 服务的使用边界

随机写令牌是本地跨站请求防护的一环，不是多用户远程登录系统。`--public-url` 的 Host/Origin 限制也不能认证非浏览器客户端；README 已告知不要开放匿名公网，所以不把“没有远程用户系统”算作当前功能缺陷。若未来改变部署用途，需重新设计认证、限流、请求体读取超时和资源配额，不能仅更改监听地址。

## 7. 人类用户、AI 与后续开发评估

### 7.1 用户流程

普通“输入 → 快速扫描 → 观察 → 精确导出”路径短且可操作。高级参数已收在弹窗，观察结果和外部规则分开，空缓存有下载入口；默认不自动合并全部第三方分类，这些设计有效。

实际卡点主要是 A02 的停止入口、A03 的探索覆盖误解、A04 的保存失败、A05/A06 的状态失效和 A16/A17 的最后一步指引。没有依据认定所有页面文字普遍臃肿；应针对这些位置改短提示，而不是再增加解释卡片。对 CDP/PCAP、DNS、Provider 等术语可保留帮助说明，让默认流程不依赖用户先理解它们。

### 7.2 AI / Vibe Coding

当前代码是公开、常规 Go/React/TypeScript 项目，架构、数据模型、API 路径和测试入口可读，没有发现代码混淆、专门拒绝 AI 访问、强制模型厂商账号或模型内容审核接口。API 写令牌和公网目标限制是安全边界，不能为了 AI 易用而删除。

阻力在于长行 JSX、少量未接入 API/配置样例、重复的默认值/版本信息，以及当前开发脚本偏 PowerShell。这些会增加人工和 AI 的检索/补丁成本，但不是无法维护。公开的贡献指南、机器可读 API 契约、Linux 原生命令示例可作为后续增强，见扩展清单。

无法从本项目代码保证所有 AI 平台都无使用/审核限制；目标网站登录、反自动化、验证码和第三方可达性也不受本项目控制。本轮没有登录真实账号、解验证码、绕过访问控制或执行支付/消息/上传业务。

### 7.3 未来可开发性

主要业务已分为 scanner/security/rules/matcher/exporter/storage，导出基于统一模型；Windows 细节以平台文件隔离，核心服务不是只绑某一块硬件。整体具有继续扩展基础。

未来增加来源时，现有 manager 中的来源分支、许可证判断和导出归属映射需要一起修改，可在确有第三来源需求时抽适配器；不必现在就造通用插件框架。增加导出格式也应保留类型化规则与来源，不在前端临时拼字符串。A05/A06 表明快照版本与临时状态的边界应优先理顺。
